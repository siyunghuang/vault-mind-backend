## Verified Problems

### Model Delivery Is Buffered

The backend providers currently wait for complete upstream responses and emit the resulting answer as one `token` event. Gemini/NVIDIA and local requests explicitly disable streaming; OpenAI also reads a complete response. Tool events may arrive earlier, but SSE transport does not itself provide incremental model text.

The frontend can fix presentation now. Genuine incremental generation requires the separate backend follow-up described below. Never create a timed typing effect to conceal buffered delivery.

### The Custom Parser Can Lose Content

`formattedBlocks` in `/home/yung/MyGitRepo/vault-mind/src/App.svelte` replaces its active list when the list type changes without first preserving the accumulated items. It also trims indentation and rewrites whitespace to guess list boundaries. Mixed and nested lists can therefore lose project names or structure. `inlineSegments` supports only a small subset of Markdown.

### The Display Adds Delay and Collapses Lists

The frontend drains four characters every 16 milliseconds even after the server has delivered the answer. This delays completion and repeatedly reparses incomplete Markdown. Separately, `section.content` is inserted into a plain paragraph, so its Markdown and line breaks are displayed incorrectly.

## Required Rendering

### One Markdown Renderer

1. Add `markdown-it` to the frontend dependencies. Use it through the proposed shared Markdown component for both assistant text and supplemental section content.
2. Remove `formattedBlocks`, `inlineSegments`, and their ad hoc whitespace rewriting. Keep the original received Markdown unchanged in message state.
3. Configure raw HTML off (`html: false`), hard-break conversion off (`breaks: false`), automatic linkification off, and typographic substitution off. Use the normal Markdown feature set, including tables and fenced code blocks.
4. Only inject HTML generated by this configured renderer. Never pass model output or raw tool results directly to Svelte's `{@html}`.
5. Retain Markdown link validation. Block executable protocols such as `javascript:`, `vbscript:`, and `data:`. If links open a new tab, add `rel="noopener noreferrer"`.
6. Support headings, paragraphs, ordered/unordered/nested lists, emphasis, links, blockquotes, tables, inline code, and fenced code blocks. Scope renderer styles so they also apply to generated HTML inside the component.

Render the accumulated Markdown on each scheduled visual update, not individual chunks as separate Markdown documents. Incomplete delimiters may temporarily appear as text. Do not remove them or alter the raw answer; the final render must exactly reflect the completed Markdown. Syntax highlighting and extra Markdown plugins are not required for this fix.

### Answer First, Details Second

- Show the assistant's answer as the primary content in the existing message area.
- Put nonempty `sections` in a native, initially collapsed `<details>` disclosure titled `Vault details`. Render each section's title and Markdown inside it. Do not create a separate floating card for every folder inside the message.
- Show `sources` as compact references after the answer/details. Use `source.path` as identity, deduplicate by path, and display `source.title` when useful. For generic names such as `README.md` or `state.md`, add the parent capsule name to the label.
- Make the full path available on focus/expansion and allow it to wrap. Do not rely only on a hover tooltip or truncate away the information needed to identify a note.
- Build Obsidian source links from the known vault name and encoded vault-relative file path, not a relative path passed as an absolute OS path. For this deployment, the vault is `AI-Memory-Storage`; use the `obsidian://open?vault=...&file=...` form. Keep the vault name in one frontend configuration value. If it is unavailable, offer a copy-path action instead of a broken link.
- Only generate Obsidian source links from source metadata. Do not infer citations from arbitrary answer text or automatically execute links/tool commands found in notes.
- Keep errors near the affected answer. Show a readable message first; place error code, status, and request ID in secondary diagnostics. A chat error's `status_code` is event metadata, not necessarily the HTTP response status.

## Required Streaming Client Behavior

### Parse Transport Frames Correctly

Add `eventsource-parser` to the frontend dependencies and use it in `/home/yung/MyGitRepo/vault-mind/src/lib/vaultMindApi.ts` instead of splitting network chunks manually. Decode bytes with one streaming `TextDecoder`, flush it at EOF, and feed decoded text to the SSE parser.

The parser must handle events spanning reads, several events in one read, CRLF line endings, comments, multiline `data:` fields, and UTF-8 characters split across byte chunks. Parse JSON only after the complete SSE event has been assembled. Ignore unknown event types for forward compatibility; malformed JSON or invalid recognized event payloads must stop the operation with a readable stream error. Do not dispatch a partial unterminated frame at EOF as a successful event.

Extend the existing helper with an optional fourth argument containing `signal` and `onRequestId`. Keep the current three-argument calls valid. Pass `signal` to `fetch`; read `X-Request-ID` and call `onRequestId` once response headers arrive. Do not serialize these options into the chat request body. Event callbacks should update state synchronously; do not start independent delayed typing queues inside callbacks.

Release the stream reader in `finally` and cancel any outstanding reading when stopping early. Do not retry a chat automatically.

### Handle Events Without Losing State

| Event | Required action |
| --- | --- |
| `token` | Append string `content` exactly once to raw answer text. Empty content is a no-op. |
| `tool_call` | Show an actual tool activity indicator using the provided tool name. Do not append it to the answer. |
| `tool_result` | Mark that activity complete. Do not display raw tool payloads in the answer. |
| `sources` | Store the supplied metadata, deduplicated by path. |
| `sections` | Store the supplied sections; render their content through the shared Markdown component. |
| `error` | Set failed state, preserve received answer text, show the error, and stop loading. |
| `done` | Flush pending visual updates and end loading. Mark completed only if the message has not failed or been cancelled. |

After an `error`, ignore later answer text for that request while allowing the following `done` to close it cleanly. EOF without `done` is `stream_interrupted`, unless an earlier backend error or intentional cancellation already explains the termination. Never overwrite a useful backend error with a generic EOF error.

### Message State and Rendering Schedule

Use a stable assistant message ID and one request controller per submission. Track these states on the message:

| State | Trigger |
| --- | --- |
| `waiting` | Submitted, with no answer text received yet. |
| `receiving` | First nonempty answer chunk received. |
| `completed` | `done` received without a preceding failure/cancellation. |
| `failed` | Backend error, invalid stream, network failure, or premature EOF. |
| `cancelled` | User stops the request. |

Remove `TYPEWRITER_DELAY_MS`, `TYPEWRITER_CHARS_PER_TICK`, and the delayed drain queue. Maintain the accumulated raw answer synchronously; schedule at most one visual update per animation frame. Flush the last pending update on completion, error, or cancellation so already-received text is not discarded. Cancel scheduled callbacks on component destruction and prevent stale callbacks from modifying another message.

Add a Stop control while a request is active, using the existing Lucide icon library and an accessible label. Abort the request on Stop and component destruction. User cancellation is not a network-error alert. Preserve the partial answer and permit a subsequent submission.

Use factual waiting feedback such as `Waiting for response`. Show specific vault activity only after receiving a corresponding tool event. Current grounding does not emit progress events, so do not claim it is reading a specific note. Remove rotating claims such as `Trying harder` or `Almost there` that are unrelated to actual events.

## Separate Backend Follow-Up

This frontend work does not turn the current one-chunk model responses into real incremental generation. A subsequent backend task must consume upstream text deltas and forward them as the existing `token` events.

That task must preserve tool rounds, reconstruct complete tool-call arguments before executing a tool, keep timeout/cancellation handling, capture usage when supplied, and send the existing terminal events. OpenAI Responses, Gemini/NVIDIA chat completions, and local provider streams have different wire formats and require their own handling.

The frontend must accept both a single complete answer event today and many incremental events later. Do not add fake server-side chunking or browser-side typing delays as a substitute. No new frontend event schema is required for the rendering fixes in this handoff.
